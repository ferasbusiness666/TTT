## Automatic Cloudinary cleanup (Cloudflare Pages Function)
- Fero asked for deletion to be automatic rather than a manual chore, so the site now has its **first piece of server-side code**: `functions/api/delete-image.js`, a Cloudflare Pages Function (free on the current plan, no separate hosting).
- **Why a server was unavoidable:** deleting a Cloudinary asset is signed with the API secret. A static page has nowhere safe to keep one, and shipping it to the browser would let anyone wipe the whole media library. The function reads it from a Cloudflare environment variable, so the secret never enters the repo.
- **Who's allowed to call it:** the caller must send a signed-in staff member's Supabase access token, which the function hands to Supabase to verify. An anonymous request gets `401`, so the public endpoint is useless to visitors.
- **What now cleans itself up automatically:**
  - deleting a post removes its cover photo **and** every Cloudinary image inside its body — the post's images are read *before* the row is deleted, since afterwards there's no record of which files it owned;
  - replacing a cover deletes the one it replaced, both after a save and when a cover is re-picked before saving.
- Cleanup is **best-effort by design**: if it fails, the post is still deleted and the site is fine — a leftover image is untidiness, not breakage. Failures are logged to the console rather than shown to the writer.
- Verified: the public-id parser handles plain, transformed (`f_auto,q_auto,w_900`), un-versioned and query-string URLs, and returns nothing for non-Cloudinary links so a stray value can't be sent to the API. The signature follows Cloudinary's spec (alphabetically-sorted params + secret, SHA-1).
- **Not live until configured** — the five environment variables in `05-known-issues.md` must be added in Cloudflare and the site redeployed. Until then the endpoint returns a clear "Server not configured" error instead of failing silently.

## Cloudinary photo uploads wired
- **Cover photos and in-body images now upload to Cloudinary** from the editor (`assets/ttt-upload.js`), and the post stores the hosted URL. Setup details and the reasoning behind an unsigned preset are recorded in `02-tech-stack-and-decisions.md`.
- **Fixed a real bug in passing:** the cover photo used to preview and then silently vanish on save, because nothing was ever written to `cover_image_url`. The editor now tracks the hosted URL separately from the on-screen preview, so what you see is what gets saved. Removing a cover clears it properly, and editing a post restores its existing cover.
- **Body images are no longer base64.** They were being embedded as data URLs inside the post HTML, which would have bloated every row in the database and slowed the article page down. They're uploaded and referenced by URL now.

- **Delivery is optimised, not just stored:** `tttPosts.cdn()` injects `f_auto,q_auto,w_*` at render time — cards ask for 900px, the article hero 1600px — with the raw URL kept in the database as the single source of truth. Images also carry `loading="lazy"` and the post title as alt text.
- **Verified end to end against the real account:** an unsigned upload lands in the `ttt-posts` folder with an unguessable ID; a `.txt` and a `.txt` renamed `.png` are both rejected (Cloudinary checks contents, not the extension); and a 4.3MB photo is delivered at 370KB through the transformation — **11.6× smaller**. Every test asset was deleted afterwards; the folder is empty.
